# Test files permitted to issue a REAL `fetch` from jsdom (ADR 0661).
#
# SHRINK-ONLY. Adding a line means a unit test is making a live network call —
# which is legal here only as a recorded exception, never as a default. Removing
# one is an ordinary PR and the point of the file.
#
# WHY THIS EXISTS: an unmocked `fetch` has no symptom. The component under test
# silently enters a failure branch the test never asked for, and whether it does
# so before or after the assertion is a race — load-sensitive in the normal lane,
# deterministic in the +365d date-bomb lane. One instance cost about a day across
# two sessions and was attributed in turn to worker starvation, contention,
# missing cleanup, `isolate: false`, and file ordering. None of those was it.
#
# THE USUAL CAUSE: a `vi.mock('…Client.js', async (importOriginal) => ({
# ...(await importOriginal()), … }))` factory that overrides most exports and
# misses one. The real function then runs. Check what the component calls that
# your factory does not name.
#
# Paths are relative to frontend/react/ and must exist — see
# scripts/check-live-fetch-allowlist.mjs.
#
# 59 entries. This number is a LOWER BOUND, not a census: it came from observing
# one full run, and some of these calls are FIRE-AND-FORGET effects that race the
# end of the test — `failedReadDecisions.test.tsx` did not fetch during the
# measurement run and does fetch in others, on an unchanged tree. So expect the
# guard to surface further files for a while. Each is a one-line addition here,
# and that is the mechanism working, not a regression.
