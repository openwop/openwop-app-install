# feature.crm.nodes

## Full description

_Moved from `pack.json` `description`, which the v2 manifest schema caps at 1024 characters._

CRM feature node pack — contact-triage nodes (the two basic/enriched variants back the CRM toggle's A/B bindings) PLUS the full ctx.features.crm surface: nine role:"action" read nodes (companies / deals / tasks / a saved segment's live members / suppression-cause analytics / bookings / sign status) and thirteen role:"side-effect" write nodes (create/update contacts, convert a lead, create companies/deals, move a deal's stage, create/complete tasks, log an activity, sync Gmail). Every write calls the SAME service function the HTTP routes call, emitting the same host event + audit row — agent/workflow writes and human writes are indistinguishable to the audit trail. Creation nodes default to a deterministic `<prefix>:<runId>:<nodeId>` id when the caller omits one — a PER-RUN dedupe key (a retried node converges), NOT a cross-run fork guard. v1.4.0 adds `gmail-sync` (scheduler-fired Gmail inbox → CRM activity sync, refs-only metadata, matched contacts only, never creates) and `suppression-summary` (suppression-cause analytics, counts only, no PII). Read nodes are role:action (recorded → replay-served); tenant+org-guarded (CTI-1). v1.5.0 adds segment-vocabulary + validate-segment (ADR 0265 CDP-C — the segment-author closed-world grounding pair; role:pure, deterministic). v1.9.0 adds persist-segment (ADR 0265 CDP-C — the copilot's draft→validate→persist write; role:action, surface re-validates + fail-closes on an invalid draft). v1.10.0 (ADR 0627 D1/D5): the 13 write nodes are role:"side-effect" + `side-effectful` — the derived floor/served set is what stops a `mode:'replay'` fork from re-executing them (a `branch` fork re-runs the tail live by design) — each with ADR 0525 input/output schemas; `gmail-sync` (now role:"side-effect" — it writes activities AND the sync row's own status) pins the sync row's owner-verified `connectionId` on every connector invoke (no user→org→workspace fall-through at the broker), keys its cursor on the typed `logGmailActivity` outcome (`logged | duplicate | capped | failed`), pauses itself on `capped`, marks `needs-reconsent` when the pinned connection is refused, and refuses to run a paused / needs-reconsent sync.
