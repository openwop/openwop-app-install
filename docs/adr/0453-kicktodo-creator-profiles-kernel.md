## Boundaries audit (verified file:line)

- **Creator profiles live in `kicktodo-community`, in their OWN store — off the kernel.** `communityService.ts:26-37` `CreatorProfile{tenantId, creatorSubject, handle, displayName, bio, links[], state, approvalId?, …}`; `communityService.ts:39` `DurableCollection('kicktodo-creator-profiles', key=${tenant}::${creatorSubject})` + a `kicktodo-handle-index` CAS-claim collection (`:45`).
- **They are exactly the kernel's shape — mutable single-current-row public pages.** `upsertProfile` (`:110`) rewrites in place; each edit resets `state:'draft'` (`:138`) and re-enters the `community-profile` approval (`submitProfile` `:158`, separation-of-duties in `applyProfileDecision` `:177`); `publicProfileByHandle` (`:205`) serves `{handle, displayName, bio, links}` for `approved` only, on its own authed route (`routes.ts:116`). **Not localized** — `bio`/`displayName` are single free-text values, no `localizations`.
- **Contrast confirms the fit (ADR 0430):** challenges are version-keyed, immutable, contentHash-frozen, enrollment-pinned (`challengeService.ts:21,258-269`) — correctly OFF-kernel. Creator profiles are the opposite (mutable, one current row, public page) — a **good kernel candidate**, the same category as `cms.page`/`commerce.product`.
- **The kernel façade seam is proven and self-wiring.** `kernelAdapter.ts:68` `makeKernelAdapter` + `entitiesService.ts:618` `mintSystemType` / `:745` `putSystemEntity` / `:711` `casSystemEntity`; `neverPublic` gate at `publicRead.ts:66`; per-locale overlay via `localizations` + `localizable` field flag validated at `entitiesService.ts:565-596`, resolved for the public wire by `toPublicEntity`→`resolveLocalizedValues` (`entitiesService.ts:885`) gated on the `entities-localization` toggle + `host/contentLocales`. Reference façades: `cms.page` (`cmsService.ts:207,251`), `commerce.product` (`commerceService.ts:305,322`). Registering one is four wiring points (ensureType, adapter, kind-validators, appMigrations move) — **no central registry to collide with.**

## Decision

Model the **approved, public** creator profile as a system-type façade **`kicktodo.creator_profile`** through `makeKernelAdapter`, while the **draft/approval write-model + handle uniqueness stay in `kicktodo-community`** (they are KickTodo policy, not kernel concerns).

- **Kernel entity** `kicktodo.creator_profile` — fields `handle` (non-localizable, the public slug), `displayName` + `bio` (`localizable:true`), `links` (JSON in `ext`). `publicRead`-eligible, NOT `neverPublic`. Its kernel `status` mirrors the approval state: `approved` → `published`+`publicRead`; any other state → not public (the entity is absent/unpublished). This reuses the ONE public gate (`gatePublicType`: `published && publicRead && !neverPublic`) and, for free, the crawler-prerender resolvers.
- **Write path:** `applyProfileDecision(approve)` calls `putSystemEntity`/`casSystemEntity` to publish (or `deleteSystemEntity`/unpublish on suspend); `upsertProfile` edits still reset to draft and pull the public entity down until re-approved. The `kicktodo-handle-index` CAS claim stays the uniqueness authority (kernel doesn't enforce handle uniqueness).
- **Localization win:** `displayName`/`bio` become `localizable`, so a creator can offer a Spanish/French/pt-BR bio, negotiated per visitor via the kernel's existing locale resolution — the capability profiles have zero of today.

## PRD-vs-architecture corrections
- **Keep the approval state machine + handle-index in kicktodo-community.** The map said "creator profiles → kernel"; the honest scoping is *the public projection* goes on the kernel, not the whole write-model. Folding approval/handle-claim into the kernel would fork policy the kernel doesn't own. The kernel is the **published-content + l10n + public-read** layer; the community feature stays the **workflow + uniqueness** layer — the same split `cms.page` uses (workflow status drives kernel `status`).

## Data model
New system type `kicktodo.creator_profile` (kernel-owned rows). `CreatorProfile` (community store) unchanged except it now also drives a kernel put/cas on approval. `kicktodo-handle-index` unchanged.

## Alternatives weighed
- **Leave profiles in their own store + hand-roll localization**: rejected — duplicates the kernel's l10n overlay + public-read gate + prerender that already exist; exactly the "second copy" ADR 0446 forbids.
- **Move the whole write-model (approval included) onto the kernel**: rejected — approval/handle-uniqueness are KickTodo policy; the kernel has no opinion on them (see correction).

## Open questions
- OQ1: `links[]` — store as an `ext` JSON blob (blind-stored, `buildSystemExt`) or model as repeatable kernel fields? Start `ext` blob (no kernel schema for repeatable URLs today).
- OQ2: does suspending a profile `deleteSystemEntity` (hard) or unpublish (status flip, retain for un-suspend)? Unpublish — reversible, matches the draft-on-edit behavior.
- OQ3: handle change — the kernel entity id is `creatorSubject`-keyed (stable), `handle` is a field, so a handle rename is a field update + a new index claim; confirm no dangling public URL (301 from old handle).
