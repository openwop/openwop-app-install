## Decision

Ship a **`knowledge-sync` feature-package** that binds an external-drive **folder** (via a Connection) to a **target KB collection** (a project's Sources collection, or any KB collection), and ~~a **scheduled executor run**~~ **a daemon-ticked in-process procedure (`runKnowledgeSyncOnce`)** that diffs the folder against per-source state and syncs changes into the KB through the existing ingest+extraction path. Content is untrusted; egress is SSRF-guarded; ~~the run is the state machine~~ **the `SyncSource` ROW is the state machine** *(**CORRECTED 2026-08-24 (feature-31 closeout, `KSWF-1`)**)*.

### Data model — one config entity + per-file diff state

```
SyncSource                          // org-scoped config
  { id, tenantId, orgId,
    connectionId,                   // → ADR 0024 Connection (provider: google | microsoft365)
    provider,                       // 'google' | 'microsoft365' (OneDrive)
    externalFolderId,               // the Drive/OneDrive folder to watch
    collectionId,                   // target KB collection (a project's Sources collection or any KB col)
    cadence,                        // schedule (ADR 0025) — e.g. every 15m / hourly / daily
    status,                         // active | paused | error
    lastSyncedAt?, lastError?,
    runId? }                        // the most recent sync run

SyncFileState                       // per (sourceId, externalFileId) — the diff cursor
  { sourceId, externalFileId,
    documentId,                     // the KB doc id this file maps to (`sync:<sourceId>:<fileId>`)
    revision }                      // etag / modifiedTime last ingested
```

### The sync run (NOT sync)

> **CORRECTED 2026-08-24 (ADR 0605 Tier 7, `KSWF-1`).** The five numbered steps below are an accurate description of what `knowledgeSyncRunner.runKnowledgeSyncOnce` does. Only the framing is false: it is **not** a run, not an executor run, and `knowledge-sync.run` does not exist as an id, a definition, or a registration. Read the steps as a procedure. Two of them have also since changed — step 4 no longer prunes from a listing that could not be proved complete (ADR 0605 Tier 1), and step 5 now persists a per-pass `lastRun` summary (Tier 6).

~~`knowledge-sync.run`~~ `runKnowledgeSyncOnce` (an in-process procedure, daemon-ticked or manual "Sync now"):
1. **list** — `knowledgeSourceFetch.listFolder(connection, externalFolderId)` → `[{fileId, name, mimeType, revision}]` (paginated, capped).
2. **diff** — vs `SyncFileState`: NEW (no state) / CHANGED (revision differs) / DELETED (state exists, file gone).
3. **fetch + ingest** each NEW/CHANGED file → bytes → `ingestDocument({collectionId, title:name, contentBase64, contentType:mimeType, contentTrust:'untrusted', documentId:\`sync:<sourceId>:<fileId>\`})` (extraction reused). Update `SyncFileState.revision`.
4. **prune** — DELETED files → `deleteDocument(documentId)` + drop the state row.
5. record `lastSyncedAt` + per-file outcomes on the `SyncSource`.

Long-running / paginated → the run handles retry + cancel. Cost/rate-limit caps per OQ-3.

### RBAC & isolation
Org-scoped (ADR 0006): managing a `SyncSource` needs `workspace:write` in the collection's org + USE rights on the Connection (ADR 0024 §use-gate). The scheduled run is tenant-trusted (the strategy precedent), scoped to the source's org/collection. Uniform 404 on insufficient scope.

## Alternatives weighed
1. **A bespoke sync daemon + OAuth + fetch.** Rejected — quadruple `no-parallel-architecture` violation (Connections + scheduler + knowledgeSourceFetch + KB ingest already exist).
2. **Webhook/push (Drive change notifications) instead of polling.** A good *future* optimization (Drive `changes.watch`), but adds a public webhook + channel lifecycle. v1 = scheduled diff (simple, works for both providers); push is OQ-4.
3. **Real-time per-file watch.** Out of scope; the heartbeat cadence is the contract.

## Open questions
1. **OQ-1 — Deletion semantics.** Hard-delete the KB doc when the source file is removed, or soft-archive? Propose hard-delete (the KB mirrors the folder) with a per-source "keep on delete" opt-out.

   > **CORRECTED 2026-08-24 (ADR 0605 Tier 7) — say this plainly, because it is the most consequential falsehood in this record: the hard-delete shipped and its own stated mitigation NEVER DID.** `runKnowledgeSyncOnce` calls `kbService.deleteDocument` per pruned row. There is **no** per-source "keep on delete" opt-out: **zero** code hits repo-wide — no field on `SyncSource`, no route parameter, no `PATCH` key (`PATCH …/knowledge-sync/:id` accepts `includeMedia` only), no UI control, no i18n string, no test. The half of the proposal that made hard-delete acceptable was the half that was never built, and because this line lives in *Open questions* it reads to every subsequent reader as a decision still being weighed rather than one already taken irreversibly in production.
   >
   > **Does this batch change that? NO — and it deliberately does not.** ADR 0605 makes the deletion *honest* (disclosed before you bind a collection, confirmed on the media toggle, persisted and rendered after every pass, and refused outright when the folder listing could not be proved complete). It does **not** make the deletion *optional*. A tenant who wants a Drive folder mirrored into a collection that also holds hand-uploaded documents still has no supported way to get one; the drive is the source of truth and hand-uploaded documents in a bound collection are destroyed on the next pass. Filed **OPEN** as `KSU-22` (`docs/steward/UX-ASSESSMENT.md`) — and the honest framing is that OQ-1 is not open, it is **half-decided and shipped**: re-opening it means either building the opt-out or amending the ADR to withdraw it, not "deciding later".
   >
   > Two related lifecycle holes are also OPEN and are the same wound from the other direction: deleting a sync source **orphans** every document it ingested (`KSC-10`), and deleting the KB collection leaves the source `active`, reporting clean `unchanged` passes into a collection that no longer exists (`KSC-11` / `KSWF-12`).
   >
   > **RESOLVED 2026-08-31 (/architect ruling — OQ-1 is CLOSED, not open; the "keep on delete" opt-out is WITHDRAWN, closing `KSU-22`).** Decision: **hard-delete-on-prune is FINAL.** Rationale: a KB collection bound to a source is a one-way **mirror** by design; a per-source retain flag manufactures orphaned, dual-authored state with no coherent cursor semantics (a retained doc either lingers as a permanent DELETED-flagged no-op prune every pass, or is dropped and re-ingested as NEW if the file returns). The shipped ADR 0605 honest-framing set (up-front disclosure, media-toggle confirm, persisted run summary, refuse-on-incomplete-listing) is sufficient mitigation for the ACTUAL destructive surface, which is narrow, gated, and re-syncable.
   >
   > **This note ALSO corrects an over-statement in the two paragraphs above (and in the `pruneWarning` UI copy), which BOTH claim prune "destroys hand-uploaded documents on the next pass" — it does NOT.** Verified on `origin/main`: `diffFolder` derives `toPrune` SOLELY from the source's own `SyncFileState` rows — `knowledgeSyncService.ts:694-696`, `states.filter((s) => !seen.has(s.externalFileId))`. A hand-uploaded document has **no** `SyncFileState` row (only the sync ingest path writes them), so it can **never** enter `toPrune`. The only docs hard-deleted are ones THIS SOURCE synced whose source file is gone from a *proven-complete* listing — and those are re-syncable by restoring the file (deterministic `documentId = sync:<sourceId>:<fileId>`). The genuinely-unserved case — "seed a collection once and keep those docs after their source file is removed" (import-not-mirror) — is an explicit **non-goal**, revisitable as its own ADR if tenant demand appears.

## RFC verdict (Step 5)
**Host assembly over Accepted RFCs + implemented ADRs — NO new RFC.** Connections (RFC 0046 credentials), the scheduler, trigger-ingestion (RFC 0099), and SSRF egress (RFC 0076) are all Accepted; folder-listing + diff + the `SyncSource` config are non-normative host extensions under `/v1/host/openwop-app/*`. A new RFC is warranted only if a normative cross-host "sync source" advertisement is later required.

> **Image OCR via a vision LLM (2026-06-23, opt-in):** `extractTextFromBytes` OCRs images (png/jpeg/webp/bmp/tiff/gif) by asking the host MANAGED provider's VISION model to transcribe them (`ocrImageViaLLM` → `dispatchManagedChat`, the in-service pattern `cms/translate.ts` uses) when `OPENWOP_KB_OCR_ENABLED=true` (default OFF — it bills provider tokens, governed by the managed daily usage cap). No local OCR engine (tesseract.js removed). Off ⇒ images 415; a non-vision managed model or provider error ⇒ 422. Replay-safe: every path that reaches it is a non-recorded service op (KB routes + the sync runner); the recorded-run media path (notebooks audio) stays on `ctx.callAI`. Applies to manual upload + drive sync alike. Follow-on: audio/video transcription (the recorded-run `callAI` path) + a vision-provider fallback.
