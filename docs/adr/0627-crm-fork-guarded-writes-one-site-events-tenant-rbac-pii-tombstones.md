# ADR 0627 — CRM: fork-guarded write nodes, lifecycle events from ONE site each, tenant-scope RBAC on the tenant lane, PII-safe merge tombstones, and an honoured Gmail connection pin

Status: implemented 2026-09-03 (feature loop 2026-09, iteration 4 — CRM; closes `CRMWF-1..6` from `WORKFLOWS-ASSESSMENT.md`, `CRM-6`, `CRM-15`, `CRM-19`, `CRM-20`, `CRM-22`, `CRM-25` from `CODEBASE-ASSESSMENT.md`, and the backend half of `CRM-UX-17` from `UX-ASSESSMENT.md`, all dated 2026-09-02)

Extends ADR 0008 (CRM), ADR 0208 (CRM orchestration wiring — the host-event seam this ADR reshapes), ADR 0209 (merge/unmerge tombstones), ADR 0252 (Gmail sync), ADR 0580 (record-lifecycle seam), ADR 0582 (egress-on-reject), ADR 0464 (subject erasure); composes ADR 0617 / 0622 / 0624 (the loop's lifecycle-event shape: ONE emit site per transition, transition-guarded, ids-only; `{ silent }` seed lane; the pack↔surface parity witness), ADR 0572 (side-effect floor), ADR 0525 (pack schema ids), ADR 0024 §4 (`actingUserId`), ADR 0028 (connection allowlist choke). Host work only — no wire change.

## Context

The 2026-09-02 passes graded the feature B− (workflows), C+ (code), B+ (UX). The five prior code Blockers closed in #3326 all held. The residual risk sits in five places that batch did not touch, and each is a Blocker on its own lane:

1. **13 CRM write nodes are outside the fork guard (`CRMWF-1`).** `packs/feature.crm.nodes@1.9.0` declares `create-contact`, `update-contact-stage`, `update-contact-owner`, `convert-contact`, `create-company`, `create-deal`, `move-deal-stage`, `create-task`, `complete-task`, `log-activity`, `persist-segment`, `booking-create-link`, `sign-request` as `role:"action"` with no `side-effectful` capability. The floor generator binds `role:"side-effect"` ∪ `side-effectful` only (`scripts/gen-side-effect-floor.mjs:52-54`), so only `gmail-sync` is guarded (`sideEffectFloor.generated.ts:297`). The executor's fork branch (`executor.ts:970-979`) re-executes the others live, and the pack's `idFor = <prefix>:<runId>:<nodeId>` (`index.mjs:57-60`) keys on the FORK's `runId`, so a `:fork` of `crm-ops.route-new-lead` mints a second follow-up task and a fork of `sign-request` re-creates an e-sign request (emailing signers, `signService.ts:236`). Six consumer chains in nine other packs end in `create-task` and inherit it. The pack header (`index.mjs:447-448` "fork-safe — no re-mint") and the surface header (`surface.ts:8`) claim the opposite.
2. **`host.crm.contact.created` is emitted by 2 of 5 contact-creation lanes (`CRMWF-2`).** `emit.ts:5-6` claims the route handlers and the surface verbs are "the two entry paths that exist"; the forms→CRM sink (`formsSubmissionSink.ts:38`), CSV import (`orgRoutes.ts:808`) and the anon lead-capture tool (`agentTools.ts:409`) call `contactsService.createContact`/`ensureContact` directly, which has zero emit sites. The chain advertised as "auto-route every new lead" never fires for the three lanes that produce leads. The 59 route/surface emit sites (`CRMWF-4`) are the generator of this class.
3. **A read-only workspace member can mutate the entire tenant-scoped CRM (`CRM-6`).** `routes.ts` never calls `requireTenantScope`; its 14 mutators gate on `requireEnabled` (toggle + entitlement, `:92-104`) alone — contacts create/patch/delete, identifiers, merge-proposal, unmerge, **direct `POST /contacts/:id/merge`** (bypassing the steward approval lane), export, triage (spawns a run), field defs, segments, suppressions. The default membership role is `viewer` (`accessControlService.ts:266,638`). `agentTools.ts:133-139` `tenantGate` is a second copy of the toggle check that also omits `checkEntitlement`. `GET /runs/:runId` (`:461`) has neither.
4. **Merge-tombstoned source contacts keep raw PII, are unreachable by any DSAR key, and get a fresh retention window (`CRM-19`).** `tombstoneContact` spreads the full row and writes `updatedAt: now` (`contactsService.ts:475-479`); `reindexContact` re-points every identifier at the survivor (`crmMergeService.ts:163-167`), so an email-keyed DSAR resolves to the survivor and `eraseCrmSubject` leg 6 anonymizes only `contacts.get(subjectKey)` (`erasure.ts:228-240`); the purger ages on `updatedAt`. This was the unfixed "Related" half of `CRM-3`, closed in the tracker without the code.
5. **Gmail sync can read another person's mailbox, drops silently at the cap, and never self-pauses (`CRM-15`).** `connectionId` is returned by the surface (`surface.ts:477-481`) but never read by the node (`index.mjs:319-405`); the invoke contract has no pin (`connectorsAdapter.ts:23-30`); `selectAuthorizedConnection` falls through `userConn ?? orgConn ?? wsConn` (`connectionsService.ts:280-286`), so a user connection flipped to `needs-reconsent` falls to the WORKSPACE Google connection. `logGmailActivity` catches the 5,000-cap 409 and warns (`gmailSyncService.ts:424-430`); the node advances the cursor unconditionally (`index.mjs:389-403`); `syncGmailNow` ignores `paused` (`:369-378`).

Also folded because they share files with the above: `CRM-22` (no email-uniqueness guard on `createContact`), `CRM-20` (single-hop erasure reach — a documented ADR 0622 decision needing a CRM-local resolver + a witness), `CRM-25` (delete cascades leave tasks/activities dangling — the fact `CRM-UX-17`'s consequence copy needs), `CRMWF-3` (catalog 15 of ≥39 types behind a prefix-blind gate), `CRMWF-5/6` (arg-parity vacuous for CRM; 0/27 schemas).

> 1. **Silent lanes are wider than "bulk + seeds", and a purge is one of them.** The retention purger (`contactsService.ts` `purgeExpiredContacts`) deletes with `{ silent: true }` — the same budget reasoning as import (a nightly sweep must not start N bound runs), decided in the build. So the silent set is **import, the webinar participant sync, the demo seeds, AND the retention purge**. A webhook or trigger-binding consumer MUST NOT rely on `host.crm.contact.deleted` to observe purges; a retention-driven deletion is observable only through the ADR 0464/0580 erasure + lifecycle seams, never through this event.
> 2. **`convertContact` also emits `contact.updated { changed: ['stage'] }`** (via `updateContact`) alongside its own `contact.converted` — the stage move is a real row change and rides the ONE `updateContact` site; a binding on `contact.updated` sees one event per conversion.
> 3. **`changed` is a DIFF, not the patch's keys** (review S1). The first cut computed `changed` as `Object.keys(patch)`, so a value-equal re-PATCH emitted `updated` and re-triggered every bound workflow — contradicting the "idempotent re-PATCH ⇒ no event" witness this paragraph promises. Every `update*` now computes `changedFields(prev, next)` on the pre-image vs the landed row and emits ONLY when non-empty; `crm-lifecycle-one-site` pins a no-op re-PATCH ⇒ 0 `updated` for deal, contact and task. Two further payload decisions: `merged` carries the absorbed id as **`sourceEntityId`** (a named ids-only key — `changed` is field names, never ids), and both unmerges emit `updated { changed: ['mergedInto'] }` (review S5); `requestSignature` threads the surface's `origin` so a chain bound to `sign-request.created` cannot re-trigger itself (review S3).

Witness: table-driven over the 16 routes + the segment tools — a `viewer` member of a shared `ws:` → 403, an `editor` → 2xx, the personal-tenant owner → 2xx; anon capture unchanged. The `SUPP-2` deferral is superseded (`workspace:write` IS the tenant-level scope).

> 2. **`tenantGate`'s `personalTenant` must be the REQUEST's, never re-derived** (review S2). The build derived it from `getUser(actingUserId)?.tenantId`; an anon session's principal is `session:<sid>` (`middleware/auth.ts`) with no user row, so the two segment tools refused the caller inside its OWN `anon:<sid>` sandbox while the HTTP lane granted it via `isOwnPersonalWorkspace`. **D4 — `CRM-19` / `CRM-20`: merge tombstones are PII-safe and erasure-reachable.** (a) `tombstoneContact` does not refresh `updatedAt` (`crm-pii-controls.test.ts` pins nothing on tombstone clocks). (b) `eraseCrmSubject` leg 6 also anonymizes every tombstone whose `mergedInto` chain resolves to the subject — walked over `mergeEvents.listForTenantIndexed` survivor→source edges with the `resolveContactSurvivor` guard shape (visited set + 32-hop bound, `contactsService.ts:156-160`); cycles cannot arise (`mergeContacts` refuses a tombstoned source or survivor `crmMergeService.ts:112-126`; unmerge deletes `mergedInto` `:450`). (c) `eraseCrmSubject` resolves an `@`/`+`-shaped key through the tenant-scoped `cdp:contact-ident` index (which returns ONE contactId per `(tenant, type, norm)` — the survivor; (b) supplies the tombstones) before treating it as a contactId — so a by-userId erasure whose resolver yields the email reaches the contact WITHOUT a host-level 2-hop fixpoint (ADR 0622's over-erasure reasoning stays honoured). Witness: erase the survivor → the source tombstone carries no address; erase by userId → the contact holding that email is anonymized; a tombstone's purge clock is its pre-merge `updatedAt`.

**D5 — `CRM-15`: the Gmail connection pin is honoured at the broker; the cursor is honest; a dead or capped sync pauses itself.** (a) The invoke path is `ctx.connectors.invoke` → `ConnectorsAdapter.invoke` request (`connectorsAdapter.ts:23-30`) → `brokeredFetch` (`connectorInvoker.ts:139-147`) → `resolveConnectionCredential` → `selectAuthorizedConnection` (`connectionsService.ts:262-285`); the request gains `connectionId?: string`, threaded to `ConnectionSelectInput`, and a pin is EXACT: return that connection iff `status === 'active'`, same provider, owned by the acting user (or org-shared with `connections:use`) — never the `userConn ?? orgConn ?? wsConn` fall-through when a pin is given. The node passes the sync row's owner-verified `connectionId` (`gmailSyncService.ts:63,212-215`). (b) `logGmailActivity` returns a typed outcome (`logged | duplicate | capped | failed`); the node advances the cursor only on `logged | duplicate`. (c) **`GmailSyncStatus` widens to `'active' | 'paused' | 'needs-reconsent'`** (`gmailSyncService.ts:56,272-273`); on `capped` the node ALSO writes the row `status:'paused', pausedReason:'capped'` — the scheduler has no failure count or backoff (`scheduleDaemon.ts:119-140` fires per tick), so a typed failure alone would re-fail forever; on a `needs-reconsent`/revoked connection the run writes `status:'needs-reconsent'`; `syncGmailNow` and the node refuse `paused`/`needs-reconsent` with a typed error. The Connections seam gains **`fireConnectionStatusChanged({ status:'needs-reconsent' })`** on `host/connectionLifecycle.ts` (the existing `fireConnectionRevoked` is a REVOKE event and must not be overloaded); `crm/feature.ts` subscribes to both. The SPA Gmail tab renders the two new states. Witness: a user whose connection is `needs-reconsent` and whose workspace has a Google connection → the sync refuses (no fall-through); cap-hit → cursor unchanged + row paused; sync-now on a paused sync → typed refusal.

**D6 — `CRM-22` and the deal CAS.** `createContact` claims the normalized primary email in a `crm:contactkeyclaim` row via `compareAndSwap(null, next)` (insert-if-absent, `hostExtPersistence.ts:659-661` — the `convertService` claim shape, `:11-14,38-43`; NOT a CAS on the ident row, which `reindexContact` writes and re-points with plain `put`); a duplicate returns 409 `validation_error` with the existing id in `details`; `ensureContact` maps that 409 to "return the existing survivor" so the anon/webinar/commerce lanes race safely; contacts without an email are not claimed (stated); a secondary `identifiers[]` email held by another contact is NOT claimed in this ADR (stated). > **CORRECTION (2026-09-03, post-implementation review of the D6 commit — one Blocker, three Shoulds folded).** Three sentences above were wrong once measured. (1) *"a stale claim is taken over"* — the first cut read a claim whose holder ROW was not yet readable as stale, and `createContact` claims BEFORE its `store.put`, so under 5 ms of write latency the loser of the CAS(null) race read the winner's missing row, took the claim over, and **two contacts landed** (witnessed with a storage proxy; the in-process sqlite hid it). A missing holder now counts as **in flight** for `CLAIM_INFLIGHT_GRACE_MS` (60 s) from `claimedAt`; only a foreign-tenant or tombstoned holder is immediately takeover-able, the takeover is a CAS on the old claim, a failed put releases its claim, and `ensureContact` re-reads by email once before surfacing the 409. (2) *"the 409 is scoped to CREATE"* — the PATCH lane then minted exactly the duplicate the create lane refuses; an email PATCH is now gated identically (claim before the put, release the old address after). (3) *"secondary `identifiers[]` emails are not claimed"* stays true, but they are still not **creatable over**: after the claim lands, an address the `cdp:contact-ident` index resolves to a live contact other than self (a legacy pre-claim row, or a survivor that absorbed it on merge) releases the claim and 409s naming that contact — otherwise `reindexContact`'s plain put silently re-pointed the survivor's identity at the new row. Erasure leg 6b deletes a key-set claim only when its holder is on the erased chain or not live (a different person's re-created address keeps its claim), and the merge re-points the source's claim BEFORE tombstoning it. Duplicate review's remaining population is therefore legacy rows and merge/import shapes, which is what it exists for.

**D7 — `CRM-25`: cascades follow the existing unlink-and-keep semantics.** `deleteContact` does NOT cascade today; the ONE CRM consumer of the ADR 0580 delete seam, `deals-crm-unlink` (`deals.ts:126-133`), unlinks `contactId`/`companyId` and keeps the deal — the same choice forms (`:216`) and webinars (`:41`) made. Deleting activities on company delete would destroy the org's timeline, so this ADR registers `tasks-crm-unlink` and `activities-crm-unlink` consumers mirroring the relink slices (`tasks.ts:180`, `activities.ts:172`): drop the dangling pointer, keep the row. The SPA's five delete confirms (`CRM-UX-17`) say "its deals, tasks and activities are kept and unlinked" — never "deleted". (Task deletion on delete is a NEW semantic this ADR deliberately does not introduce.)

## RFC verdict

**Host-extension — no RFC.** `host.*` events are the host's namespace (RFC 0086 §E); pack roles/schemas ride the Accepted RFC 0013 format; replay serving is the standing `replay.md` req 4 contract; the connection pin is a host broker field.

## Alternatives weighed

1. **Keep `role:"action"` and fix `idFor` to key on the source run id.** Rejected: the executor would still re-execute the node on a fork (a live call to the store per node), and the pack would still be lying about its classification; the floor is the mechanism, `idFor` the backstop.
2. **Per-row `contact.created` on import.** Rejected: 10k runs from one CSV; a batch `imported` event + a chain that reads the batch is the honest shape (stated in the recipe).
3. **Add a `crm` role tier instead of `workspace:write`.** Rejected: the scope exists; a new tier is the `SUPP-2` category error the deferral warned about.
4. **A host-level 2-hop erasure fixpoint for `CRM-20`.** Rejected here (ADR 0622's over-erasure reasoning stands); the CRM-local index-backed resolution reaches the contact without widening any other eraser.
5. **Honour the pin in the node instead of the broker.** Rejected: the broker is the ADR 0028 choke every consumer flows through; a node-level check would be bypassable by the next consumer.
