# ADR 0622 — Invitation lifecycle host events + `feature.orgs.nodes.invite`: a chain can react to a joiner and invite one into this workspace

Status: implemented (2026-09-02 — backend + packs; the ADR 0564 P2–P3 recipient/inviter UI + the `/grade-ux` rows ship in the frontend unit of the same PR; see § Implementation record) (feature loop 2026-09, iteration 2 — Org invitations; closes `OIWF-1`, `OIWF-2`, `OIWF-3` from `WORKFLOWS-ASSESSMENT.md` § "Org invitations (ordinal 2) — 2026-09-02", and states the policy `ORGINV-9` asked for)

Extends ADR 0004 (org invitations) and ADR 0564 (invitation decline — flipped to `Accepted` by this iteration and implemented alongside); composes ADR 0208 §1 (the ONE host-event seam + bindings), ADR 0617 (the leaver twin: `features/users/emit.ts`, `surface.ts`, `packs/feature.users.nodes`, the self-trigger guard, the catalog parity gate), ADR 0024 §4 (`actingUserId`), ADR 0572/0555 (side-effect floor + steward manifest), ADR 0464 (subject erasure). Host work only — no wire change.

## Context

The invitation flow is a fail-closed token transaction and is CORRECTLY not a chain: mint (`features/orgs/invitationsService.ts:110-150`, hash-only at rest, replace-at-mint, index row first), deliver inline through the inviter's own brokered email connection (`inviteDelivery.ts:47-95`, send-once key `org-invite:<inviteId>`), accept (`:232-307`, tenant/org/role from the token row, claim-by-delete, `createMember`, restore-on-failure). The 2026-09-02 `/grade-workflows` pass re-verified that: doctrine PASS, zero pin sites, zero feature timers, expiry on the sanctioned retention daemon.

What the pass could not pass is the seam question ADR 0617 made measurable: **can a tenant bind a chain to a joiner, and can a chain invite someone into this workspace?** Both answers are no:

- `features/orgs/` calls `emitHostEvent` zero times; the host-event catalog (`frontend/react/src/settings/hostEventCatalog.ts:38-87`) has 49 types across 14 features and no `host.orgs.*`.
- `FEATURES.md:169` Packs "—" is accurate: no `feature.orgs.nodes`, no `ctx.features.orgs`, and no `accessControl` workflow surface either. `examples/workflow-chain-packs/people-hr/pack.json` `people-hr.onboarding` (plan → approve → {itProvision M365 `createUser`, hris `create-worker`, tickets} → track → notify) provisions a new hire everywhere EXCEPT this workspace, and nothing can start it from an acceptance.
- ADR 0564 (decline) has been `Proposed` since 2026-08-14 with zero code; the recipient's only refusal is silence and the inviter cannot tell "unseen" from "refused".

The `/grade-code` pass added the policy question this ADR must answer (`ORGINV-9`): the accept gate's "MUST own the invited email" compares `user.email` (`invitationsService.ts:256-258`), a field `PATCH /users/users/:id` sets with no verification (`users/routes.ts:228-247`) under the implicit personal-owner short-circuit — so a personal-tenant user can rename themselves to the invitee's address and accept a token they hold. Token possession remains the real credential; the docblock overstates the email check.

## Decision

> **REVIEW CORRECTIONS (2026-09-02, `/architect` pre-implementation pass — 2 Blockers, 6 Shoulds folded; the review RAN the seven baseline suites, 107 tests green).** The first draft (a) put the `created` emit at the route where `superseded` is not derivable and where the node lane would have been silent, and cited `revokeInvitation` as the replace-at-mint caller (false — the deletes are inline at `invitationsService.ts:123-124`); (b) copied ADR 0617's tenant-wide `assertTenantScope` for an ORG-scoped decision (a manage-holder in org A could have invited into org B); (c) wrote a `ORGINV-9` rule that would have refused nearly every legitimate accept — `updatedAt` is bumped on EVERY login (`usersService.ts:269`) and the OIDC lane never writes `email` at all (`authRoutes.ts:73`, `usersGuards.ts:107`); (d) gave the node lane no source for the accept link's base URL; (e) had no CAS on decline, no pre-claim status check on accept, and no `declined` branch on preview; (f) an email-keyed eraser that a userId-keyed erasure request cannot reach. All corrected below; the review is the record.

> **Consequence, stated (review S4, 2026-09-02).** `track` is an `all_success` fan-in (`executor/scheduler.ts` — the default `triggerRule`: all upstreams terminal, none failed). A typed refusal from `invite-host` (no `OPENWOP_PUBLIC_BASE_URL`, an undeliverable invite, a disabled / erased / non-durable acting user) therefore **fails the whole run** — after `itProvision`, `hris` and `tickets` have already provisioned in parallel behind the same gate; nothing is rolled back and a re-run re-provisions them. This is the cost of joining the fan-in rather than dangling a second terminal (alternative 3's family): the operator MUST confirm `OPENWOP_PUBLIC_BASE_URL` + a connected email sender BEFORE starting the run (README § Recipe step 1, now stated as such). A fan-in rule that tolerates one failed upstream is a chain-format change (RFC 0013 / RFC 0134), not a wiring one, and is not made here.

**D4 — ADR 0564 implemented as designed, with the concurrency it lacked.** `status?: 'pending' | 'declined'` + `declinedAt`; `POST /invitations/decline { token }` registered OUTSIDE `h` like accept (`routes.ts:224-233`), same gate chain (invite-tenant toggle, expiry, email-ownership, signed-in — a recipient without an account must sign up to decline; the terminal copy says so). **The decline write is a `compareAndSwap` on the pending row** (`hostExtPersistence.ts:659`): a blind `put` racing the accept's claim-by-delete would RESURRECT the row as declined for someone who joined, and two concurrent declines would emit twice. **`acceptInvitation` refuses `status === 'declined'` BEFORE the claim at `:268`** so the attempt does not burn the row (uniform-invalid answer, per ADR 0564). **`previewInvitation` (`:201-230`) gains a `declined` branch** — `InviteError.reason` (`:83`) += `'declined'` on preview + accept (disclosure is fine: the token holder declined it) and the accept page gains a `declined` phase. `listInvitations` already returns declined rows and `toClientInvite` spreads `status`/`declinedAt` (verified); kvAgeOut reaps on `expiresAt` (verified); nothing else indexes by email (verified). Open question 1 answered: no cooldown; a re-mint over a declined row carries `superseded: true` + `previousStatus: 'declined'` on `created`.

**D5 — `ORGINV-7` without breaking the pinned semantics.** `createInvitation` KEEPS replace-at-mint (two direct-caller tests assert 1 row / 1 index pointer after two mints, `orgs-invitations.test.ts:106-115,138-150`). The NEW composition owner `createInvitationAndDeliver` = **precheck (no-sender, moved from `routes.ts:134-144` and kept BEFORE any mint — `orgs-route.test.ts:221-240` asserts 422 `{reason:'undeliverable', cause:'no_sender'}` + an empty list) → mint WITHOUT replace → deliver → on `sent` (or a non-prod `skipped` where the token is echoed) supersede the prior rows; on a prod `skipped`/`send_failed` roll back the NEW row via `revokeInvitation` (row then index, `:160-161` — the between-state is a fail-closed miss, the ORGINV-5 rationale) and leave the prior invite untouched**, and the 422 says the earlier invitation is still valid (new key; the resend confirm copy `orgs/i18n/en.ts:148` stays true on success). Stated window: between mint and supersede two tokens are live for (org, email); a crash there leaves two rows until the next mint's replace loop. Non-prod token echo stays a route concern (`exposeTokens()` `:46`); the surface never returns the token. Witness: prod mode, prior pending invite, inviter with no connection → 422 AND the prior token still previews.

**D6 — `ORGINV-8`: the invitation store gets a SubjectEraser that is actually reachable.** `registerSubjectEraser('orgs:invite')` handles BOTH keys the row carries: `inv.email === key.toLowerCase()` (delete index-first) AND `inv.createdBy === key` (scrub `createdByName` — a declared PII field, `usersService.ts:33` — and tombstone `createdBy`). Reachability, stated: an email key reaches erasers only via the consent DSAR route (`consent/routes.ts:221`); the users erase route passes a userId (`users/routes.ts:347`) and no `SubjectKeyResolver` maps userId → email. This ADR adds a users-feature resolver (`getUser(key)?.email`, store-backed) so erasing a joined user by id also reaches pending invites to their address — noting that the resolver hands the email key to every other email-keyed eraser (CRM, analytics); that widening is deliberate and recorded.

> **CORRECTED 2026-09-02 (review S3) — "every other email-keyed eraser (CRM, …)" overstated the reach.** `resolveSubjectKeys` (`host/subjectErasure.ts`) is **single-hop**: every resolver is given the ORIGINAL key, and the keys they return are not fed back through the resolvers. The users resolver turns a `userId` into that row's email; the CRM eraser (`crm/erasure.ts`) filters by `contactId`, and the CRM resolver that maps an email → `contactId` only ever saw the `userId`. So what a by-userId erase now **additionally** reaches is exactly the erasers keyed DIRECTLY on the email: **pending invitations to that address (`orgs:invite`) and analytics events keyed by the email**. It does NOT reach CRM contacts. A 2-hop fixpoint would close that, and is deliberately NOT added here (over-erasure risk through heuristic links — the ADR 0381 rule); the manifest note (`host/subjectEraserManifest.ts` 88→89) says the same. Coverage: move `orgs:invite` from `RECORDED_DEBT` (`subject-erasure-feature-stores.test.ts:393`) to `EXPECTED_COVERED` (`:368`) and add the manifest edge (`host/subjectEraserManifest.ts`).

**D7 — `ORGINV-9`: the email-ownership policy, stated and made testable.** The token is the credential; the email match is defense-in-depth. `User.emailProvenance?: 'idp' | 'admin' | 'self'` is written ONLY at the three email-write sites: `createUser` (`'idp'` iff `source ∈ {oidc, saml, scim}` and an email was supplied, else `'admin'`), `upsertFromPrincipal` when `input.email !== undefined` (`'idp'` — the SAML/SCIM/test-seam lanes), and `updateUser(email)` with the PATCH route passing `'self'` when the actor is the target or is acting under the implicit personal-owner short-circuit, else `'admin'`. The accept AND decline gates require `email` matches AND `emailProvenance !== 'self'`, else `403 forbidden` + `reason: 'email_unverified'` (the docblock's "MUST own" replaced by this rule). Tests: login after mint → OK; a shared-workspace admin PATCHes a member's email → OK (vouched); a personal-tenant self-PATCH → 403 `email_unverified`; SAML-refreshed → OK. **Residual, recorded:** the OIDC bind never carries the IdP email (`Principal`, `types.ts:56-60`, has no email; the bind passes none) — an OIDC user's only email today is admin-set; that is a users-feature gap filed as `USERS-20`, not closed here.

> **CORRECTED 2026-09-02 (review B1 — Blocker) — the "residual" above was not residual; it made accept UNREACHABLE for the production sign-in lane.** On a personal (`user:`) tenant the ONLY email-write path an OIDC human had was `PATCH /users/users/:id` under the implicit-owner short-circuit, which D7 correctly stamps `'self'` → `403 email_unverified`; a shared-workspace admin cannot vouch because the row lives in the personal tenant (`users/routes.ts` 404s on a foreign tenant); `PATCH /users/me` is displayName-only. So every OIDC user on this host was refused by the gate this ADR introduced, and the suite could not see it because every test signs in through `routes/authTestSeam.ts`, which passes an email → `'idp'`. **Fixed in the same PR (USERS-20):** `middleware/oidcVerifier.ts` surfaces `email_verified`; `middleware/auth.ts` sets `req.oidcEmail` from `claims.email` **only when `email_verified === true`**; the bind route (`users/authRoutes.ts`) and the lazy canonical fold (`usersGuards.resolveCallerUser` → `resolveCanonicalUserForTenant` / `applyIdpEmail`) write it with `emailProvenance: 'idp'`, replacing a weaker (`admin`/`self`) or absent address; an unverified claim is dropped at the middleware, so it can never overwrite an IdP email. Witness: `test/orgs-invite-accept-oidc.test.ts` — NO test seam, a real bearer against the synthetic issuer: `email_verified:true` → accept 201, member created; `email_verified:false` → no email stored → 403 `email_unverified`. **Residual, stated honestly:** an IdP that does not assert `email_verified` (or a Firebase email/password account whose address was never confirmed) leaves the row address-less; a personal-tenant user has no admin to vouch for them, so the accept page's copy (`orgs/i18n/*.ts` `acceptErrorUnverified`, ×4 locales) now says "sign in through your identity provider so your verified address is used, or contact the person who invited you" instead of pointing at an administrator who cannot exist. `USERS-20` stays open in `CODEBASE-ASSESSMENT.md` for that residual (a host verification-email flow, alternative 5).
>
> **Also corrected (review S1):** `createUser` used to derive `'idp'` from `input.source ∈ {oidc,saml,scim}` — and the admin `POST /users/users` takes `source` from the REQUEST BODY, so a personal-tenant owner could POST `{ principalId:'saml:x', source:'saml', email:<victim> }` and mint an "IdP-asserted" row for any address. Provenance now comes from the LANE: `createUser` takes `emailProvenance` explicitly (omitted ⇒ `'self'`), the admin POST passes `'admin'` or `'self'` under `isOwnPersonalWorkspace`, the SCIM provisioner / demo seed / IdP first-login funnel pass theirs. **And (review S2):** deviation "legacy rows with no provenance pass" was fail-open — a row with NO provenance now reads as `'self'` (`effectiveEmailProvenance`), and app migration **20** (`stamp-user-email-provenance`, `backfillEmailProvenance`) stamps every unstamped row once from its lane: `'idp'` iff `source ∈ {saml, scim}`, `'self'` iff `isPersonalTenantId(tenantId)`, else `'admin'` (`source:'oidc'` is deliberately NOT `'idp'` — that lane never wrote an email before USERS-20).

## RFC verdict

**Host-extension — no RFC.** `host.*` events are the host's namespace (RFC 0086 §E); node packs ride the Accepted RFC 0013 pack format; the decline route is under `/v1/host/openwop-app/*`.

## Alternatives weighed

1. **Emit from `revokeInvitation` (the service) instead of the route.** Rejected: it is also the D5 rollback primitive, and replace-at-mint deletes inline (`invitationsService.ts:123-124`); only the admin revoke is a business event.
2. **A `member.added` event on `createMember`** instead of `invitation.accepted`. Rejected here — that event belongs to the accessControl owner (three other `createMember` callers) and is a separate ADR; `accepted` carries `memberId` so a chain can join the two later.
3. **Put the invite node BEFORE `approve`** in onboarding. Rejected: the same ADR 0200/0582 gate rule ADR 0617 D3 followed.
4. **Client-only "dismiss"** for decline — rejected by ADR 0564's own bar.
5. **A verification-email flow for `ORGINV-9`.** Deferred: it is a users-feature decision; D7 closes the cheap, IdP-provenance half and states the residual.

## Open questions

- [ ] Should `listInvitations` on the surface expose `email` to a run (it is PII, and the route does return it to a manager)? Default: **no** — the surface returns `inviteId` + `role` + `status` + `expiresAt` only; a chain that needs the address holds it as its own parameter.
- [ ] `accepted` on the `alreadyMember` branch: does a bound welcome chain want to distinguish it? It can (`alreadyMember: true` is in the payload); no second event kind.

### Deviations from the decision text, stated

- **D5 — the 422's "new key".** The prior-invite fact rides `details.priorInviteStillValid: true` (a boolean) plus a message sentence, NOT a new `reason`/`cause` value and NOT the prior `inviteId`: the existing `reason`/`cause` pairs are what the invites UI already maps to copy, and the error envelope REDACTS high-entropy strings in `details` (a UUID-shaped id came back as `inv:<redacted:high-entropy>` in the first run of the witness), so the id could never have reached the page; the prior row is listable anyway.
- **D2 — `revokeInvitation` on the surface emits nothing.** D1 names the admin ROUTE as the ONE `revoked` site, so a workflow-driven revoke is deliberately silent (the node's output schema says so). If a bindable "revoked from a run" event is wanted later, the honest shape is a second composition owner like D5's — not a second emit site.
- **D3 — the chain-config ratchet vs. a REQUIRED whole-value param.** `chain-config-conformance` expands every chain with `params: {}` and counts a config key whose whole-value token resolved to `undefined` as MISSING when the node's config schema lists it under `required`. `invite.config.json` therefore leaves `email` OPTIONAL (the `feature.users.nodes` `userId` idiom — inputs-or-config precedence with a typed refusal on empty), so the ceiling stays at 42 while `newHireEmail` is `required` on the CHAIN. `chain-embed-deferred-parity` pins the whole-value position (dropped in both modes when unset, the value when set) rather than an embedded-marker row, because a whole-value token never freezes to `MISSING_REQUIRED_MARKER`.
- **D2 — `role: "action"` + `side-effectful` on `revoke-invitation`.** The decision text called list/revoke "action nodes"; revoke additionally carries the `side-effectful` capability so the derived floor holds it (a re-executed revoke on a fork would 404 rather than duplicate, but serving the recorded outcome is still the right posture). `list-invitations` is `read`.
- **D7 — legacy rows.** ~~A `User` row with no `emailProvenance` (pre-D7) passes the gate; only an explicit `'self'` is refused.~~ **RETRACTED 2026-09-02 (review S2): that was fail-open** — any write that omitted the field was a free pass. A missing provenance now reads as `'self'` (refused), and app migration 20 stamps the legacy rows once from their lane (see the D7 correction note), so "refuses nearly every legitimate accept" is avoided by the stamp, not by a pass.
- **D6 — the resolver skips email-shaped keys.** `usersEmailKeyResolver` returns `[]` for a key containing `@` (an email key is already the email) and never matches heuristically; it expands a userId to that row's stored address only.
