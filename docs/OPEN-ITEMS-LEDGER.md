### 54-8 / ADR 0554 P4 — traced to the end, and the answer is IMPLEMENTATION, not qualification

Traced 2026-08-18. The compensation transition is a **read-check-write**, not a CAS:
`resolveObligationLocked` does `rows.get` → `expectedState` check → `canTransition` check → **unconditional
`rows.put`**. It is serialised only by `withObligationLock`, which is a **`Map<string, Promise>` — an IN-PROCESS
mutex**. And `DurableCollection` exposes only `get`/`put`: **there is no CAS primitive to call.** The code's own
comment states the consequence of losing the lock: *"two concurrent unwind passes each fired the inverse."*
Reachable across instances via the §E operator routes, which any instance serves over HTTP.

**But this is ALREADY RECORDED DEBT, not a discovery — and I nearly reported it as one.** ADR 0554 says it in
three places: `:1000` *"The claim is scoped to WITHIN ONE INSTANCE"*, `:1258` lists *"Cross-instance 'exactly one
wins'"* among what is NOT done, and `:1469` *"P4 is where the cross-INSTANCE half is qualified, and it needs the
conditional write."* I had the finding assembled and the message half-written before checking whether the ADR
already said it. It did, precisely, including naming the missing primitive.

**What that changes about 54-8, and it is the useful part:**

- The state-boundary half is **not** "test whether the CAS holds". The ADR already states it does not. A
  single-process test of it would assert the half that works and imply the half that doesn't — the overclaiming
  shape again.
- **The real work is adding a conditional write to `DurableCollection` and routing `resolveObligation` through
  it.** That is implementation, and it is what actually closes P4's cross-instance half; the qualification test
  follows the fix rather than substituting for it.
- The other three halves (duplicate delivery, replay/fork, crash-at-boundary *within* an instance) remain
  single-process testable and genuinely open.

**Method note worth more than the finding:** the check that saved this was `grep -niE "single.instance|
cross-instance"` over the ADR *before* writing the report. Three of tonight's near-misses have been this shape —
assembling a correct mechanism and failing to ask whether it was already known.

### 51-2 / ADR 0551 P3 — the item is NOT "nobody got to it". It is not doable as written without a decision.

Investigated to the end 2026-08-18. Three measured facts, none of them inferred:

1. **Run creation commits the outbox intent in the SAME transaction as the run row**
   (`routes/runs.ts:457`, `enqueueDispatch: true`), and the `setImmediate` dispatch is explicitly "a wakeup
   hint". So a durable intent genuinely survives the accepting instance's death — the property P3 wants to
   qualify really is there.
2. **Every booted instance sweeps AND executes.** `runDispatchSweeper.ts` reads **no** env vars at all, and a
   repo-wide grep for a read-only / no-execute / sweeper-disabled mode returns **nothing**. There is no supported
   way to boot an instance that accepts work without executing it.
3. **Recovery of a run whose executor died is gated by the 12-minute orphan lease**, not the 60s outbox lease —
   because once an instance starts a run it holds `RUN_DISPATCH_LEASE_MS`, which derives from the ADVERTISED
   `capabilities.limits.maxRunDurationMs`.

**Consequence.** A two-process "kill the worker mid-run" test is either ~12 minutes long, or a RACE whose
duration is 10s or 12min depending on whether `setImmediate` beat the `SIGKILL` — and a test whose runtime forks
on a race is precisely the timing-dependent test I refused to ship for H58's duration cap. Adding a
no-execute seam purely to make it fast is the same "test hook wearing config's clothes" we rejected for
`OUTBOX_LEASE_MS`.

**So P3 splits into two items, and only one of them is a test:**

- **The bounded recovery SLO is already knowable and should be STATED, not measured**: for a crashed executor it
  is `RUN_DISPATCH_LEASE_MS` = **12 minutes**. That is a real production property an operator must know — a
  crashed instance's in-flight runs stall for twelve minutes — and P3's "bounded recovery SLO" is arguably
  asking for exactly this number. It needs no harness; it needs writing down and, if 12 minutes is unacceptable,
  a design change rather than a test.
- **The fast, honest, achievable multi-instance test** is the OUTBOX-INTENT HANDOFF: a run whose intent was
  committed by an instance that died *before starting it* is picked up by another instance within one poll
  (≤5s + execution). That is a genuine multi-instance property, it is deterministic, and it does not need a
  seam. It does NOT qualify mid-run crash recovery, and the test must say so rather than implying P3 is closed.

**This is a decision for the ADR, not a coding task**, which is why it is recorded rather than half-built.
